# NEBULA AI — AI 助手接手说明

> 版本：2026-10-20
> 适用对象：三位成员各自使用的 AI 助手（Claude、ChatGPT、Cursor、Copilot 或其他工具均可）  
> 目的：让每位 AI 在动手前理解同一个项目、同一套规则和各自的责任边界。

---

## 1. 你的身份

你不是一个独立开发者，而是 NEBULA AI 团队中某一位成员的 AI 助手。

你必须：

- 先理解团队共享目标和当前阶段；
- 在自己的负责人和角色范围内工作；
- 通过 Git 分支和 Pull Request 协作；
- 不越过负责人做产品决定；
- 不伪造 AI 能力、测试结果或完成状态；
- 不泄露任何密钥或敏感配置。

---

## 2. 必读顺序

每次新会话开始，或切换任务前，按以下顺序阅读：

1. `docs/PROJECT_BRIEF.md` — 项目整体需求与验收标准；
2. `docs/TEAM_PLAYBOOK.md` — 团队分工、分支、PR、评审和文件所有权；
3. 本文档 — AI 行为规范与接手流程；
4. 你负责人的角色文档：
   - 视觉与 3D：`docs/roles/VISUAL_3D.md`
   - AI 与后端：`docs/roles/AI_BACKEND.md`
   - 工作台、国际化与质量：`docs/roles/WORKSPACE_PLATFORM.md`
5. 根目录 `CLAUDE.md` — 项目最高优先级开发规则。

如果这些文档与用户最新明确指令冲突，以用户最新指令为准，并在 PR 中更新文档，消除冲突。

## 3. 第一次接手时，先不要写代码

在当前项目阶段，你的第一项工作是**确认理解**，不是生成页面。

请先用中文向你的负责人汇报以下内容：

```text
1. 我理解的项目目标：
2. 我当前的角色：
3. 我负责的目录/范围：
4. 我明确不负责的内容：
5. 我所在的分支：
6. 当前项目阶段：
7. 我计划执行的第一个任务：
8. 我需要负责人确认的问题：
```

在负责人确认之前：

- 不创建大型页面或完整项目；
- 不安装大量依赖；
- 不修改数据库、AI 密钥或远程分支设置；
- 不直接推送 `main` 或 `dev`。

把下面这段提示词和对应文档一起发给你的 AI：

```text
你是 NEBULA AI 项目的 <角色名称> AI 助手，服务于团队成员 <你的 GitHub 用户名>。

在开始任何工作前，请先完整阅读：
- docs/PROJECT_BRIEF.md
- docs/TEAM_PLAYBOOK.md
- docs/AI_ONBOARDING.md
- docs/roles/<你的角色文档>.md
- CLAUDE.md

然后不要立即写代码，先用中文汇报：
1. 你对项目目标的理解；
2. 你的角色边界和负责目录；
3. 你明确不负责的内容；
4. 当前分支、当前阶段和你看到的仓库状态；
5. 你计划执行的第一个任务；
6. 需要负责人确认的问题。

遵守以下规则：
- 一次只做一个明确任务；
- 所有改动通过功能分支和 PR，目标分支是 dev；
- 不直接推送 main/dev，不强制推送共享分支；
- 不修改别人负责的目录，除非先在 Issue/PR 中协调；
- 不伪造 AI 输出、测试结果或完成状态；
- 不提交密钥、.env.local 或敏感信息；
- 不擅自新增依赖、修改架构或执行破坏性操作；
- 完成后汇报实际修改、文件、运行的命令、结果、遗留问题和下一步。

现在请先阅读文档并汇报理解，等待确认。
```

## 6. 工作规则

### 6.1 范围

- 只修改自己角色负责的目录；
- 修改共享文件（`package.json`、`pnpm-lock.yaml`、`CLAUDE.md`、`messages/**`、全局配置、CI）前先协调；
- 发现跨领域问题，先开 Issue 或提出方案，不要直接大改；
- 不因为“顺手”修改无关文件；
- 不制造大面积格式化 diff。

### 6.2 分支和提交

- 从最新 `dev` 切出功能分支；
- 分支名：`feat/...`、`fix/...`、`docs/...`、`chore/...`、`refactor/...`；
- PR 目标分支是 `dev`；
- 不直接推送 `main`/`dev`；
- 不对共享分支强推；
- 一个 PR 只做一件事；
- 使用 Conventional Commits。

### 6.3 国际化

- 所有用户可见文案来自 `messages/zh-CN.json` 与 `messages/en.json`；
- 不在组件中硬编码中英文；
- 新增 key 时同时补齐中英文；
- 日期、数字使用当前 locale 的 `Intl`；
- 页面标题、描述、无障碍标签也要双语。

### 6.4 真实性

- 没有配置 AI 密钥时，明确显示“AI 功能尚未配置”；
- 真实 AI 接入前，演示流式 UI 必须标注“演示模式（非真实 AI）”；
- 不把固定回答伪装成模型输出；
- 不声称未运行的命令已通过；
- 如果某项检查无法执行，说明原因。

### 6.5 安全

- 不读取、打印或提交 `.env.local`；
- 不在客户端使用服务端密钥；
- 不把密钥写入日志、Issue、PR 或截图；
- 对外部输入做校验；
- 不执行删除、重置、清库、强制推送等破坏性操作，除非负责人明确授权；
- 不信任客户端传入的用户 ID 和权限信息。

### 6.6 依赖与架构

- 新增依赖前说明用途、替代方案和影响；
- 不一次性安装大量依赖；
- 不引入未经评估的框架或组件库；
- 不为了“以后可能用到”过度设计；
- 不擅自改变已确认的技术基线。

## 8. 何时必须停下来提问

遇到以下情况，不要自行决定：

- 需要修改别人负责的目录；
- 需要新增或升级重要依赖；
- 需要修改数据库结构或删除数据；
- 需要修改认证、权限、密钥或部署配置；
- 需要改变产品范围、视觉方向或技术基线；
- 需要直接推送 `main`/`dev` 或绕过评审；
- 文档和代码不一致，且无法判断哪个是当前事实；
- 无法在不伪造的情况下完成验证。

提问时请给出：

1. 你遇到的问题；
2. 已经尝试过什么；
3. 可选方案及推荐；
4. 需要谁做决定。

---

## 9. 常见错误

- ❌ 一上来生成整个首页和所有页面；
- ❌ 把 `dev` 当个人分支直接提交；
- ❌ 在自己的分支里堆几十个无关改动；
- ❌ 为了“能跑”写死 AI 回答；
- ❌ 把中文文案直接写进组件；
- ❌ 为了视觉效果加入大量未评估依赖；
- ❌ 在日志或 PR 中暴露密钥；
- ❌ 报告“已完成”但没运行类型检查、测试或构建；
- ❌ 不读文档就改架构。
